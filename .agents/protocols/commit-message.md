# Protocol: commit-message

**Status:** v1
**Loaded by:** `phase-implementer`, `phase-scaffold`, `/commit` command
**Defines:** the format of commit messages and PR descriptions produced
by PILOT

---

## Purpose

Every phase produces a commit. Every spec produces a PR. The commit
messages and PR description connect the work back to the spec — six
months from now, a developer reading the git log should be able to find
the spec a commit came from in one click, and trace each acceptance
criterion to the phase that satisfied it. This protocol defines the
format that makes that traceability possible.

## Per-phase commit format

When a phase completes Gate 4 successfully, `phase-implementer` stages the
phase's `files_touched` and produces a commit with this format:

```
<type>(<spec-id>): <phase title>

Phase <N> of <M> for spec <spec-id>-<spec-name>.

<one-paragraph description of what this phase did and why>

Satisfies:
- AC-<n>: <AC title from spec>
- AC-<n>: <AC title from spec>

Refs: specs/<spec-id>-<spec-name>.md, phase <N>
```

### Fields

| Element        | Source                                              | Required |
|----------------|-----------------------------------------------------|----------|
| `<type>`       | Conventional commit type (see below)                | yes      |
| `<spec-id>`    | The spec's 4-digit hex ID                           | yes      |
| `<phase title>` | The phase's `title` from progress.json             | yes      |
| `<N>` / `<M>`  | Phase number and total phases                       | yes      |
| Description    | One paragraph; agent writes from phase context      | yes      |
| Satisfies      | List of `AC-N: <title>` from the phase's `acceptance` | yes if non-empty |
| `Refs:`        | Path to spec, phase number                          | yes      |

The `Satisfies:` block lists the AC IDs from the phase's `acceptance`
array, each resolved to its title from the spec (not the full G/W/T
block — the title alone is enough for context; the spec is the canonical
source).

If a phase's `acceptance` array is empty (e.g., a pure-refactor phase
that doesn't advance any AC directly), the `Satisfies:` block is
omitted entirely.

### Type prefixes

Use Conventional Commits style:

| Type        | When to use                                        |
|-------------|----------------------------------------------------|
| `feat`      | Phase adds user-facing functionality               |
| `fix`       | Phase corrects existing behavior                   |
| `refactor`  | Phase restructures without behavior change         |
| `chore`     | Phase is mechanical (deps, config, types)          |
| `test`      | Phase adds tests for existing code                 |
| `docs`      | Phase updates documentation only                   |
| `perf`      | Phase changes for performance reasons              |
| `build`     | Phase changes build/CI/tooling                     |

Most phases will be `feat` or `chore`. `phase-scaffold` phases default to
`chore`. The agent picks based on what the phase actually does, not on
what the parent spec is — a scaffold phase under a `feat`-level spec is
still `chore` if it only added types.

### Example

```
feat(0001): Add Session model and migration

Phase 1 of 6 for spec 0001-user-authentication.

Introduces the Session model in the Prisma schema, generates the
migration, and updates the generated Prisma types. The model holds
a user reference, an expiration timestamp, and a creation timestamp,
with indexes on userId and expiresAt to support the queries that
later phases will add.

Satisfies:
- AC-1: Unauthenticated dashboard access redirects to login
- AC-4: Sessions expire after the configured duration

Refs: specs/0001-user-authentication.md, phase 1
```

## Per-spec final commit and PR description

After Gate 5 passes (the entire spec is complete), `phase-implementer`
produces a final summary commit only if the team's workflow demands one
(e.g., squash-merging is disabled). Most teams will let the per-phase
commits stand and rely on the PR description for the summary.

The PR description is generated by `phase-implementer` at Gate 5 using
this format:

````markdown
# <spec title>

Closes spec <spec-id>-<spec-name>.

## Summary

<one paragraph from the spec's Summary section, lightly edited for PR context>

## What this PR includes

- Phase 1 — <phase title>
- Phase 2 — <phase title>
- ...

## Acceptance criteria

Each criterion below is preserved verbatim from the spec, prefixed with
the implementation status determined at Gate 5:

- **[verified] AC-1: Unauthenticated dashboard access redirects to login**
  *Covered by automated tests in phase 3.*
  > **Given** a user with no active session
  > **When** they visit `/dashboard`
  > **Then** they are redirected to `/login?next=/dashboard`
  > **And** no dashboard content is rendered before the redirect

- **[verified] AC-2: Successful login redirects to original destination**
  *Covered by automated tests in phase 4.*
  > **Given** a user is on `/login?next=/billing/invoices`
  > **When** they submit valid credentials
  > **Then** they land on `/billing/invoices`, not on `/dashboard`

- **[verification needed] AC-3: Login UI matches the design system**
  *Manual verification required — please confirm before merging.*
  > **Given** a user on the `/login` page
  > **When** they view the page
  > **Then** spacing, typography, and button styling match
  >      `design-system/auth-flow.fig`

Status labels:
- `[verified]` — covered by automated tests and Gate 5 commands
- `[verification needed]` — manual verification required (UI, visual,
  third-party integration)
- `[partial]` — partially satisfied; see notes below

## Verification

All Gate 5 commands passed:

```
<command 1>: ok
<command 2>: ok
```

## Notes from review

Findings surfaced by code-reviewer that did not block the pipeline:

- **moderate** / convention-drift in `app/api/login/route.ts:12` —
  Direct prisma import in route handler; should go through lib/db/.
  *Surfaced for developer review; not blocking.*

## Spec

specs/<spec-id>-<spec-name>.md
````

The status labels (`[verified]`, `[verification needed]`, `[partial]`)
are chosen by `phase-implementer` at Gate 5 based on what was verified:

- **`[verified]`** — the AC's `Then` clauses are covered by an
  automated test that ran (and passed) at Gate 5.
- **`[verification needed]`** — the AC describes behavior that
  automated tests cannot reasonably check (visual design, third-party
  integration that isn't safely mockable, hardware behavior). Surfaced
  so the developer can verify before merging.
- **`[partial]`** — only some of the `Then` clauses are verified. Used
  when a phase blocked or a moderate finding deferred part of the work.
  Always accompanied by a note in the "Notes from review" section.

## When commits and progress diverge

The `commit_sha` field in `progress.json` is the authoritative link
between a phase and its commit. If a phase needs to be re-implemented
(severe finding sent it back, retry ladder produced a new commit), the
old `commit_sha` is discarded and the new commit's sha replaces it.

If a phase's commit is amended or rebased after PILOT finishes (e.g., the
developer cleans up history before merging), `progress.json` becomes
stale. This is expected — once Gate 5 has passed, `progress.json` is a
historical artifact, not a live state. The PR description, not
`progress.json`, is the canonical record at that point.

## Project-specific overrides

If your project has its own commit convention (e.g., Jira ticket prefix
required, no Conventional Commits, different scope syntax), document it
in `rules/commits.md`. `rules/commits.md` overrides this protocol when
both are present — your project's conventions win.

A minimal override:

```markdown
---
applies-to: commits
description: Acme commit conventions override PILOT default
---

# Acme commit format

All commits must include the Jira ticket prefix:

\`\`\`
[ACME-1234] <type>(<spec-id>): <phase title>
\`\`\`

Everything else from PILOT's commit-message protocol still applies.
```

## What this protocol does NOT cover

- **Branch naming.** Out of scope. Use whatever your team uses.
- **PR merge strategy.** Out of scope. Squash, rebase, or merge are
  all fine.
- **Commit signing.** Out of scope. If you require signed commits,
  configure git locally; PILOT doesn't manage signing.
- **Co-author attribution.** PILOT does not add `Co-authored-by:` lines
  by default. The developer is the author of their work; PILOT is a tool,
  not a contributor. If your team prefers explicit attribution, override
  via `rules/commits.md`.
